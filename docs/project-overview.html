YHWH Transient

Project reference — architecture, requirements & status

A staff-run property management system for a staycation house, vehicle-rental, and city-tour business. Staff manage listings, inquiries, reservations, payments, and customers from one portal; the public site is browse-and-inquire only — nobody outside the business ever logs in.

● Phase 5 shipped Single property, not multi-tenant Local dev, Convex-backed

01 — Architecture

One reactive backend, no separate API layer

Convex replaces what would otherwise be a REST/GraphQL API, a Postgres database, and a migrations tool. The React app talks to Convex functions directly through convex/react hooks — there is no client fetch layer to maintain.

Houses · vehicles · tours — no login, no payment
Staff portal

Role checks, availability logic, and payment-balance math all live here, never in the client.

One listing table, three types

listings carries a type discriminator (house / vehicle / tour); each type's own fields live in a satellite details table joined by listingId. Convex indexes are per-table, so this reads cleaner than one giant union table.

Availability as half-open ranges

Booked dates are stored as [startDate, endDate) blocks and checked for overlap in application code inside the same transaction as the booking insert — Convex has no SQL exclusion constraint to lean on.

Customers deduped by contact, not name

A customer record is matched by (email, phone). Two different people can share a name, so name is never used to merge records — the customer picker disambiguates by showing contact info and last stay.

Payment balance is computed, not stored

A booking's paid/owed amount is the sum of its verified payment rows at read time, not a field kept in sync by hand — one booking can take several partial payments with no risk of the total drifting.

02 — Requirements

Staff do the work; guests never log in

The defining constraint of this system: every booking, every customer record, and every payment is entered by staff. That one rule shapes almost everything below.

Public site

Browse & inquire

  • Search and view houses, vehicles, and tours
  • Submit a non-binding inquiry (dates, headcount, contact info)
  • No payment and no availability hold at inquiry time
  • Look up an existing booking by reference number + email
Staff portal

Run the business

  • Dashboard: revenue, occupancy, today's check-ins/outs
  • Create a reservation manually, or convert an inquiry
  • Record one or more payments against a booking
  • Search, add, and review customers and their stay history
  • Manage listings, photos, and staff accounts
Access & roles

Three tiers

  • Staff — reservations, inquiries, payments
  • Admin — staff, plus listings management
  • Superadmin — admin, plus staff accounts
Explicitly out of scope

By design, not yet

  • Customer accounts or customer login — never planned
  • Self-service booking or online payment capture
  • Multi-property / multi-tenant support
03 — Process

How the system arrived here

The build went through several real pivots rather than following a single upfront spec — each one is a decision that changed the data model or the user flow, in order.

01

Scoped as a hotel-style PMS

First pass assumed a FastAPI + PostgreSQL backend and a hotel-style booking flow.

02

Reframed the business

Not a hotel — a Town Proper staycation house business that also runs Van & Car Rental and Basic City Tours.

03

Replaced the backend entirely

Dropped FastAPI + PostgreSQL for Convex as the full backend — database, functions, and auth in one system, not just managed hosting.

04

Added manual, staff-side booking

Staff needed to log phone/Messenger/walk-in bookings directly, not only through the public flow.

05

Dropped the Airbnb look-alike

Rebuilt the public UI around the business's own navy + dusty-rose crest, including a custom SVG logo mark.

06

Fixed a scroll-lock bug

The splash screen locked page scroll and never released it once its animation finished.

07

Removed self-service booking

Customers now submit inquiries only — no login, no payment, no availability hold. Only staff create real bookings, by hand or by converting an inquiry.

08

Restructured roles

Collapsed owner_admin / front_desk / housekeeping into staff / admin / superadmin, migrated via a temporary-widen → migrate → narrow schema change.

09

Turned Payments into analytics

Retired the old "verify/reject" queue, a holdover from the self-service flow, in favor of a revenue dashboard — totals, by method, by month.

10

Renamed guest → customer

Every record is staff-entered, so "guest" no longer fit. Renamed the table, fields, and UI labels throughout, with the same migrate-and-narrow pattern.

11

Built a real customer directory

Search, add, and reuse customer records from a shared picker that disambiguates by contact info and last stay instead of name.

12

Added payment balances

Bookings can now take partial payments; a booking confirms only once fully paid. Cash may run over the balance to cover a tip — GCash and bank transfer may not.

13

Kept the booking lookup locked

Considered dropping the email field from the public lookup since references are unique — kept it, since a reference code alone isn't secret enough to gate full payment history behind.
